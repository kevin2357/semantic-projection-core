# Projection Layer Architecture

**Status:** Pass 2 design document.  
**Scope:** A future layer/project for translating canonical semantic packages into target-domain models.

## 1. Core operation

```text
semantic source graph
+ context object
+ primitive mappings
+ target schema
→ projected model
```

Projection is the generalization of projected chart generation. It preserves operator structure while changing the domain of expression.

## 2. Why projection is not report writing

A report is one possible output. Projection can output prose report models, game mechanic vectors, park/trail/ecosystem models, family-system diagrams, workplace collaboration maps, publication spread content, NPC relationship matrices, or dashboard-ready traits.

## 3. Inputs

### 3.1 Source graph

Generated by the SDK. Should remain domain-neutral and provenance-rich.

### 3.2 Context object

Context answers "what is this interpretation for?"

```json
{
  "relationship_type": "manager_employee",
  "audience": "professional",
  "age_band": "adult",
  "target_domain": "workplace_collaboration",
  "tone": "analytical",
  "constraints": {
    "avoid_romantic_language": true
  }
}
```

### 3.3 Primitive mappings

Primitive mappings translate semantic operators.

```json
{
  "source": "venus",
  "operator": "attract / value / harmonize",
  "target_domain": "workplace_collaboration",
  "targets": ["morale", "values_alignment", "positive_reinforcement", "social_ease"]
}
```

### 3.4 Target schema

The target schema defines the output structure. For Mythos, this might be trait vectors and modifiers. For NCS/MPAS, terrain and trail models. For reports, section-ready narrative units.

## 4. Context examples

- Romance: Venus becomes attraction, affection, pleasure, bonding, beauty.
- Professional collaboration: Venus becomes morale, values alignment, social ease, positive feedback loops.
- Parent-child: Venus becomes warmth and soothing; Mars becomes autonomy and boundary-testing; Saturn becomes structure and safety.
- Mythos Star Game: semantic relationship traits become mechanics.
- NCS/MPAS: planetary/aspect structures become terrain, trails, ecosystems, weather, vistas, and difficulty gradients.

## 5. Age-aware projection

A chart should not be interpreted identically for a child, adolescent, adult, and elder. The chart structure stays the same; the projection target changes.

## 6. Multi-person projection

A future group report might include natal A/B/C, pairwise synastries, group composite/centroid, shared theme aggregation, divergence map, and projected group model.

## 7. Projection boundaries

Projection should not mutate source evidence. It should create a derived model with references back to source package IDs.

## 8. Future implementation

Near-term prototype candidates:

1. Synastry -> professional collaboration projection.
2. Synastry/composite -> Mythos affinity mechanics.
3. Natal -> Human OS publication model.
4. Natal -> NCS/MPAS park terrain.
5. Parent-child pair -> family-system model.

## Pre-projection boundary and projection order

Projection now begins from `canonical_astrology_graph`, not from raw ephemeris data and not from a completed orthodox report interpretation.

The canonical graph preserves source objects, source operators, topology, provenance, evidence tiers, and structural strength. A thin `structural_evidence_graph` may aggregate repeated source activation and temporal overlap before projection, but it must not assign destination-domain meaning.

The first explicit profile is `orthodox_astrology.v1`. It is ontology-preserving, but it adds orthodox themes, salience policy, conventional vocabulary, claim candidates, and report hints. The familiar astrology interpretation path is therefore explicit rather than invisible.

See `Pre-Projection Semantic Boundary.md` for the complete contract and migration policy.

## Projection input lineage requirements

Projection profiles should consume canonical relationships only after root-owner lineage has been resolved.

A projected relation must be able to trace:

```text
projected relation
→ canonical relationship
→ endpoint root owners
→ source record
→ calculated fact
```

The distinction between direct geometry and derived evidence lineage must remain visible after projection.

## Chunk 2.1 implementation status

The plain-data profile, context, request, projected graph, audit, diagnostics, and mapping-execution contracts now exist in code and JSON Schema. The generic engine and profile registry begin in Chunk 2.2.

## Chunk 2.2 generic engine status

The extraction-ready package now includes a domain-neutral engine, profile protocol, exact-version registry, mapping execution audit, unmapped-source policies, deterministic merge behavior, and output validation.

The engine accepts only plain projection contracts. Profiles provide target-domain drafts; the engine owns IDs, provenance, merging, diagnostics, audit records, ordering, and indexes. No orthodox astrology or cognitive mapping constants exist in the engine.

A small `demonstration_projection.v0` profile proves execution mechanics only. It is not one of the final Chunk 2 reference profiles.

## Chunk 2.3 reference profile

`orthodox_astrology.v1` is now implemented as a genuine profile over the generic projection engine. Core objects and major aspects map into orthodox target primitives and relationships with deterministic IDs, source refs, mapping-rule refs, relevance components, audit records, and diagnostics.

The generic engine contains no astrology mapping constants.

## Chunk 2.4 registry and context proof

Synastry package registries now enter projection through a narrow SDK adapter. The generic engine receives only plain source graphs, structural evidence, source registries, context, and options.

The same canonical relationship graph can be projected into general or professional orthodox relationship contexts with explicit context transformation evidence.

## Chunk 2.4.1 analysis selection boundary

Profile-aware representative selection belongs in the SDK analysis adapter, not the generic projection engine. The engine still projects exactly the source graph it receives; the adapter chooses a useful analysis subset and reports its coverage explicitly.

## Chunk 2.4.2 representational ID bridge

SDK adapters must not assume compact-view endpoint IDs equal canonical graph endpoint IDs. Stable relationship identity is used to cross the materialization boundary, after which projectability and provenance are evaluated entirely with canonical IDs.

## Chunk 2.5 standalone operation

Projection can now run over a saved full SDK package without invoking any astrology pipeline. SDK package extraction remains in `projection_adapter`; the generic engine receives a plain `ProjectionRequest`.

The embedded convenience API is exported from `astro_analysis_sdk`, avoiding a reverse dependency from the extraction-ready projection core back into SDK adapters.

## Chunk 2.6 second ontology proof

`cognitive_architecture_demo.v0` projects the same canonical Natal source into cognitive-process primitives and interaction relationships. It uses the same generic engine, contracts, IDs, audits, and diagnostics as `orthodox_astrology.v1`.

The profile is explicitly experimental and non-diagnostic. Its purpose is architectural proof that projection happens before target-domain relationship reasoning.

## Chunk 2.6.woof — operator, mode, domain, interface, relation

Expanded cognitive and Woofmapped reference profiles now test the richer projection composition:

```text
source operator
+ sign-derived mode
+ house-derived domain
+ angle-derived interface
+ aspect-derived relation
```

The engine required no target-domain special cases. Mode/domain data currently lives in projected object attributes, while canonical house-cusp objects can project as explicit target-domain objects. Chunk 2.7 should evaluate whether generic contracts need first-class mode/domain types before extraction.

## Chunk 2.6.woof.1 — projected term registries

Each real profile now owns a typed projected term registry. Projection artifacts embed only the used-term subset and reference entries through stable term, mode, domain, and relation refs.

This is semantic self-description at the projection boundary, not a claim/narrative layer.

## Chunk 2.7 stabilization boundary

Projection materialization is now explicit (`full`, `standard`, `summary`, `forensic`), eligible-scope coverage is distinct from canonical-source coverage, and extraction readiness is mechanically inspectable. The generic package remains free of astrology calculation imports. Repository separation in Chunk 2.8 should preserve this ownership boundary rather than redesign it.

## Static versus temporal projection

`projected_semantic_graph.v1` models a static target-domain system. It must not be used to flatten nested Transit activations.

Transit packages now fail explicitly until `projected_temporal_activation_graph.v1` is implemented. The future temporal contract references a static projected target graph and adds directional, time-bounded activation arcs, transient states, phases, repeated passes, and timing provenance.
